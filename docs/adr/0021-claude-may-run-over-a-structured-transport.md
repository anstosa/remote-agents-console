# Claude may run over a structured Transport

Claude Code has run only as its TUI in a tmux pane. It can now also be driven over the structured Transport (ADR 0015), the way Pi is: `claude -p --input-format stream-json --output-format stream-json --verbose --replay-user-messages --permission-prompts host --permission-prompt-tool stdio --mcp-config <the console's SDK server> --settings <inline JSON>` under a holder (ADR 0016), behind a Claude protocol client, shown as a transcript Panel. Which one new launches use is the operator's choice, `adapters.claude.transport` (`tmux` by default, or `structured`), and both stay. We keep both because the structured Transport gives Claude what Pi Agents already have (steer, Inline questions as messages, the model picker, the Agent panel's Conversation selector), while Anthropic may come to charge print-mode (`-p`) use differently from interactive use, and the operator must be able to go back to the TUI without losing anything.

## Considered options

- **Replace the TUI with the structured Transport.** One path to maintain, but it ties the console to `-p` whatever Anthropic decides to charge for it.
- **The Claude Agent SDK in a console-owned host program.** A second program to build against the SDK's TypeScript API and keep in step with it. The CLI's stream-json mode is the protocol the SDK itself speaks to the CLI, so driving the CLI directly needs no host program and reads the operator's settings as the TUI does.
- **A per-launch choice in the Launch menu.** Left out for now: the menu, the prepared launch choice and every launch path would have to carry the Transport. The config default covers the operator's need to switch.
- **Trust every folder in print mode, as the CLI does.** Rejected: it would load a Worktree's project settings, hooks and `.mcp.json` servers that the operator never agreed to, which the TUI asks about first.

## Consequences

- **The protocol is stream-json with the CLI's control protocol.** The console initialises the CLI, interrupts it and switches its model with control requests. Print mode has no `AskUserQuestion`, so the console serves an `ask_user` tool from an SDK MCP server (`--mcp-config` naming `rac`, its traffic carried as `mcp_message` control requests). With `--permission-prompts host --permission-prompt-tool stdio` a tool permission the CLI would prompt for arrives as a `can_use_tool` request and becomes a permission question that only the operator, answering in the console itself, may grant; an integration or the voice assistant may only refuse it, and its refusal is not passed off to the model as the operator's. What Allow grants is shown whole: the command, file content or edit, then every other input key (a timeout, `replace_all`), with `dangerouslyDisableSandbox` called out first and bidirectional and zero-width code points shown as code points. One too long to show in full can only be denied, so nothing is granted unseen. (Without `--permission-prompt-tool stdio`, which the Agent SDK passes, the CLI denies whatever would prompt rather than ask. The rules a request suggests saving are not offered, so Allow grants one call.)
- **Prompts and steers are user messages under the console's ids.** With `--replay-user-messages` the CLI echoes each and reports its `command_lifecycle` (queued, started, completed), which says when a Turn starts with a prompt and when a steer sent mid-Turn is read: folded into the Turn at the next tool call, or run as a Turn of its own once the Turn ends. A steer left over when its Turn ends stays pending until the CLI starts or completes it, since the CLI may run several leftovers as Turns one after another; one it completes unstarted, or one still waiting after a minute in which the CLI said nothing with no Turn in flight, is shown as unread, so a lost lifecycle line cannot keep the Agent busy for good. Cancelling a Turn does not withdraw a steer already sent: the interrupt names the ones it still has queued (`still_queued`, by uuid), cancels the Turn's prompt (`command_lifecycle` `cancelled`), then runs them as a Turn of their own, so they stay pending until they start.
- **The launch report rides a hook.** The inline `--settings` add one SessionStart hook that prints `{"suppressOutput":true,"rac":"<nonce>"}` from `$RAC_LAUNCH_NONCE`; the client reports in when the CLI's `hook_response` carries the launch's nonce, which stays out of the model's context. The settings are inline rather than a rendered file because Claude's sandbox protects only the session's own settings file, and a sibling of `hooks.json` would be one more console-owned file a model could rewrite. They report nothing into tmux (under a holder `$TMUX_PANE` is the holder's pane) and arm no Calendar lifecycle, which follows prompts over tmux only. The hook's output is kept in the session file, which is how the Conversation list tells a Conversation the console began over the structured Transport from a headless Review run (ADR 0010), which stays hidden. Print mode writes no generated title, so such a Conversation is listed under its first prompt until it is renamed.
- **Restrict until trusted.** Print mode takes every folder as trusted. Before every structured launch (by the operator, a restart, resume or Conversation switch, a Conductor or Davo worker) the console reads Claude's own trust record as the launch's account has it, `.claude.json` in the `CLAUDE_CONFIG_DIR` of `adapters.claude.env`, else in the launch's home, and looks up the key Claude itself keys trust by: inside git, the main worktree's top level (so a linked worktree of a trusted repository, a pull request's say, is trusted, as in the TUI), elsewhere the real folder; that exact key only, never a folder above it (a print-mode oracle against CLI 2.1.319 showed a repository or folder under a trusted one, or anything under a trusted `/`, untrusted). The parsed record is kept until the file changes, and one that cannot be read trusts nothing. Where Claude does not trust the folder yet, the console drops the operator's `--mcp-config`, `--setting-sources` and `--strict-mcp-config` and adds `--setting-sources user --strict-mcp-config` after every other argument, with a transcript notice saying how to lift it. That leaves out the folder's project and local settings and hooks, and every MCP server but the console's own (one with a relative command would run the folder's script); the operator's user-level settings, hooks included, still apply and run with the folder as their working directory. Trusting a folder stays the TUI's dialog: the console never writes the record.
- **What the operator loses** over the structured Transport: `!` shell commands and the TUI's `/model` and `/resume` pickers. The model picker and the Conversation selector replace the pickers. With no `allowedModels` configured the picker offers every model Claude lists (Pi's offers none then, as it lists every provider's); with them, only those. A model's Effort is a launch argument (`--effort`): choosing another of those the model supports restarts the process, on the Conversation once it has been saved, and not while a steer waits for the CLI.
- **The model is named on every start of the Agent's process.** Claude does not restore a Conversation's model on `--resume`, so the console keeps the Agent's model and Effort on its record (when they could be read back) and names them whenever it starts the process again (resume, restart, Conversation switch); the client takes the launch's model as the Agent's until the CLI says otherwise. A Conversation resumed by a new launch starts on the Launch menu's model, or Claude's default. Continuing the latest Conversation resumes the newest one the console lists for the folder, since `--continue` would take the newest session of any kind, a headless Review run included.
- **Claude's own sandbox and permission mode still apply.** The console does not sandbox Claude over either Transport (ADR 0004, ADR 0018): its sandbox and permission mode, `auto` included, come from the operator's settings and `adapters.claude.args`. The Launch menu's model, Effort and permission mode are composed onto a structured launch exactly as onto a pane, and the permission choice is kept on the Agent's record for its later starts; one read back from disk keeps only the options Claude's controls offer and never one that loosens the Agent past the operator's configuration (a bypass is chosen again), while restrictive ones (`plan`, `dontAsk`) stay. (A Pi Agent's `sandboxed` is restored as recorded.) Each structured launch drops from the operator's arguments what it composes itself or what would break the client or the holder (`--tools`, `--output-format`, `--bg`, `--worktree`, `--no-session-persistence`, `--json-schema` and the like; short flags combined into one, `-pc`, are not taken apart), so an Agent that outlives a change of Transport launches the same; in a trusted folder the operator's own `--mcp-config` servers still load. A structured Claude worker of the Conductor or Davo launches unsandboxed by the console, like a Claude worker in a pane; Davo spawns one only where Claude's configured Transport is structured.
- **Claude is not pinned**, unlike Pi (ADR 0017). The operator installs and updates it, so its protocol may change under the console: the client logs each record kind it does not know once and ignores it, and the launch report shows the CLI's version.
- **A Conversation switch restarts the process.** The CLI cannot switch session in place, so the console restarts it with `--resume` on the chosen Conversation and on the model the Agent was on, keeping the Agent's id and queue.
- **Not under the host bridge.** There the holder comes with Pi's host runtime, which a Claude launch cannot rely on, so `structured` falls back to `tmux` with a boot warning, and a structured Claude Agent from before is not started again (it stays Exited; launching Claude anew runs it in a pane).
- **Both Transports share Claude's session files**, so a Conversation moves from one to the other when a new launch resumes it, and changing `adapters.claude.transport` changes only new launches.
