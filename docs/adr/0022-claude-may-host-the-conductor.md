# Claude may host the Conductor

The Conductor (ADR 0018) may run as structured Claude (ADR 0021) as well as Pi, chosen by `conductor.kind` (`pi` by default), on one of `adapters.claude.allowedModels`. ADR 0018 kept the Conductor Pi-only until the console could arm or confirm another kind's sandbox and keep the console token out of that kind's commands. For structured Claude it now can, through the CLI's own control protocol, without a host program or an extension: the console writes every setting the process loads, reads the effective settings back before it gives any access, and gives the token over the protocol. Probes against Claude Code 2.1.328 (`docs/research/claude-conductor/README.md`) showed each step working, and showed a sandboxed command unable to see the Claude process at all. We chose this so that the operator can give the Conductor Claude's models without giving up any of ADR 0018's guarantees.

## Considered options

- **Keep the Conductor Pi-only.** Safe, but it limits the Conductor to the models Pi can reach, and the reason for the limit no longer holds for structured Claude.
- **Trust the operator's Claude configuration** (rejected in ADR 0018). The console would neither write nor read what confines the Conductor.
- **Layer the console's settings over the operator's** (`--setting-sources user` plus inline `--settings`). Rejected: Claude merges list settings rather than replacing them, so the probe's Conductor took on the operator's `allowedDomains` (the console's own host among them), `excludedCommands` (run unsandboxed), Bash allow rules, hooks (run unsandboxed) and plugins.
- **The Claude Agent SDK in a console-owned host program** (rejected in ADR 0021). The SDK speaks the same control protocol to the same CLI, so a host program would add a second program without adding a guarantee.
- **Claude over tmux.** The TUI has no channel to give the token over except its environment or launch line, which ADR 0018 rules out.

## Consequences

- **Only the console's settings load.** A Conductor launch passes `--setting-sources ''` (no user, project or local settings, so none of the operator's hooks, plugins or sandbox lists), `--strict-mcp-config`, `--tools Bash,Read,Edit,Write,Grep,Glob`, and inline `--settings` the console renders: the launch's nonce hook; a `sandbox` that is enabled, fails closed (`failIfUnavailable`), allows no unsandboxed command, and takes its network and filesystem lists from the shared `sandbox` configuration plus `adapters.claude.sandbox`, never allowing the console's own endpoint (ADR 0004 amendment), and keeping the operator's credentials under the home directory unreadable as a Sandboxed Pi's policy does; and `permissions` in `dontAsk` mode that allow the console's MCP tools and edits in the Conductor's Project, deny `AskUserQuestion`, and block file tools outside its working folders (`blockFileToolReadsOutsideWorkingDirectories`, `blockWritesOutsideWorkingDirectories`). The operator's `adapters.claude.args`, the Launch menu's permission mode and the untrusted-folder arguments do not apply to it; `adapters.claude.env` still does, since it names the account. Since `rac` names the console's own MCP server in a Conductor, the client serves its `ask_user` there as the SDK server `operator` (`mcp__operator__ask_user`).
- **Access follows confirmation.** Before giving access, the Claude client sends `get_settings` and refuses unless the inline settings are the only source, the sandbox is enabled, fails closed and allows no unsandboxed command, and both outside-folder blocks are in force. Only then does it send `mcp_set_servers` with the console's endpoint and the token in its `Authorization` header, once; the launch report then says the sandbox is engaged. A CLI that cannot answer either request fails the launch, as any kind that cannot take the access does. This confirms the configuration the CLI runs under, where Pi's extension confirms that its own sandbox runtime started; `failIfUnavailable` closes that gap by having the CLI refuse commands it cannot sandbox.
- **The token stays in Claude's process.** It is never in the environment or the launch line, and Claude's sandboxed commands run in their own PID namespace, where the probe found no other process visible. `mcp_status` answers echo the server's headers, so the console never logs, records or emits them.
- **The role prompt and the compaction handoff ride the protocol.** The role prompt is `initialize`'s `appendSystemPrompt`. For compaction, `initialize` registers a `SessionStart` hook callback for the `compact` source; `/compact` carries the handoff focus and the operator's instructions, and the callback answers with the console's state as `additionalContext`. The state therefore follows Claude's summary as context of its own rather than being appended inside it, as Pi's is; the Conductor reads both.
- **No code mode.** A Claude Conductor calls the console's MCP tools directly, so the script deadline (`scriptDeadlineMinutes`) does not apply to it.
- **It always runs structured.** `adapters.claude.transport` still chooses only the operator's launches. A Claude Conductor is refused under the host bridge, where structured Claude is unavailable (ADR 0021).
- **Claude is not pinned.** A CLI update that changes `get_settings`, `mcp_set_servers` or the hook callback fails the Conductor's launch closed rather than running it unconfined, with the Conductor's usual push once it fails to start three times. The probes are the re-check after an update.
- **Print-mode billing is the operator's risk.** ADR 0021 kept the TUI because Anthropic may bill `-p` differently, and an always-running Conductor is the most exposed use. Setting `conductor.kind` back to `pi` is the way out; its Conversation does not carry over between kinds.
- **Workers are unchanged.** `spawnKinds` still decides the kinds a Conductor may spawn, whichever kind it is, and only Sandboxed Pi workers carry the console's sandbox.
