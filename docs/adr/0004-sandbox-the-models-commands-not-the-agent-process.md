# Sandbox the model's commands, not the agent process

A *Sandboxed* Agent (`CONTEXT.md`) needs filesystem and network restrictions on what the model can do. The obvious realisation for an agent without a native sandbox was to wrap the whole CLI in `srt` (`@anthropic-ai/sandbox-runtime`): one mechanism for every Adapter, and `docs/research/srt-pi-tmux-verification.md` proved an `srt`-wrapped Pi runs inside a console pane. We chose instead to leave the agent process on the host and confine only the commands the model runs — the shape Claude Code's own sandbox has ("Bash subprocesses only") and the shape Pi documents for its Gondolin extension. For Pi that is a console-shipped extension that routes the `bash` tool and `!` commands through the sandbox-runtime *library* and wraps the in-process file tools with path policy; for Claude it is its native `sandbox.*` settings injected per launch. The console never wraps a command in `srt`. We chose this because whole-process wrapping has four costs that are structural, not fixable: (1) the agent's state reporter (ADR 0001) would sit inside the sandbox, and the only way to let it reach the tmux socket — `network.allowAllUnixSockets: true` — also lets the model's commands run `tmux run-shell` on the host, a complete escape; (2) bwrap's `--new-session` means the agent never receives SIGWINCH, and the console resizes panes per viewer, so a wrapped TUI keeps drawing at its launch width; (3) the runtime's mandatory-deny mount points litter the worktree with eleven zero-byte dotfiles for the pane's lifetime, which the console's dirty-tree checks (New Task, PR switch, review tour) treat as untracked files, and `kill-pane` (SIGHUP) skips the cleanup that would remove them; (4) the agent's real state directory (`~/.pi/agent`, with `auth.json` and its extensions) must be writable to the model. Confining only the model's commands removes all four: the reporter runs in trusted host code, the TUI is unsandboxed, the mount points exist only for the duration of one command (probe: none left after `kill-session`), and the state directory stays on the host.

## Considered options

- **Whole-process `srt` wrap** (the console renders `srt --settings <file> -- <program> <args>`). Uniform and verified, but see the four costs above; the reporter would need a file the console polls and relays, and stopping an agent would need a SIGTERM to `srt` before `kill-pane`.
- **Tools-only via the `srt` CLI** (one `srt` process per command). Same boundary as the chosen option but restarts the proxy per command, needs an `srt` program path and `node` on the pane `PATH`, and inherits the CLI's option-capture quirks. The library call is 10 ms and starts the proxy once per Pi session.
- **Both, whole-process as a generic fallback** for adapters without a tool-hook API. Rejected: nothing in this effort needs it (OpenCode is designed-for only), and keeping the wrap alive keeps the escape hazard alive.

## Consequences

- **The console composes nothing sandbox-specific at launch.** An Adapter with a sandbox is an Adapter whose `launch(input)` reads `input.sandboxed` and emits its own flags (`-e <extension>` plus a policy path for Pi; a `--settings` variant for Claude). The console records `@rac_sandboxed` on the pane and otherwise treats the launch like any other. ADR 0002's "wraps the command in `srt`" clause is withdrawn.
- **seccomp stays on and `allowAllUnixSockets` is never rendered.** The model's commands cannot reach any Unix socket; from inside the sandbox `tmux` reports *Operation not permitted*. The state hook runs in the agent process, which is trusted code.
- **Sandboxed defaults on and is never remembered.** Every launch of an Adapter that offers a sandbox starts sandboxed; turning it off is an explicit per-launch choice. Only the Adapter is remembered per Worktree.
- **The runtime is a console dependency**, pinned like any other, not a host install: `@anthropic-ai/sandbox-runtime` in `apps/server`, resolved by the Pi extension from the repository's `node_modules`. Hosts still need `bwrap` and `socat`; a host-bridge deployment needs the host checkout's dependencies installed.
- **Policy is static per boot**, rendered by `Adapter.files` from the operator's shared and per-kind `sandbox` keys plus the Adapter's declared needs. What varies per launch — the worktree, its git common directory, a temp directory — the extension adds at runtime from its own cwd. There are no per-launch temp files.
- **The extension fails closed.** If the runtime cannot initialise, the extension replaces the tools with ones that refuse and say why; Pi is never silently unsandboxed.
- **What is not confined**, and is documented: the agent process itself (its provider traffic, its own state writes), tools registered by other extensions the operator has installed, and processes a command leaves running (they die with the command, as under Claude's sandbox).
- **Ghost dotfiles are transient** — present during a command, removed by `cleanupAfterCommand()` after it — so no `.git/info/exclude` entries are written. Revisit if leftovers from a hard kill ever become a problem.

*Amended 2026-10-27 for Pi driven over its RPC mode (ADR 0017):* there is no state hook; the console-shipped extension is loaded on every Pi launch, Sandboxed or not, and also sends the launch report and registers the console's MCP server. Sandboxed commands get an allowlisted environment (a base set plus the operator's `sandbox.env` names), not Pi's, so provider keys and the MCP token never reach them, and the MCP endpoint is never an allowed domain. The console's Pi loads only what the console vets: `-ne` keeps the operator's own extensions and packages out (each can be opted back in with `-e` in `adapters.pi.args`), only the console's MCP server starts, and `--no-approve` keeps a Worktree's `.pi/` settings and MCP servers out while its skill and prompt directories are passed explicitly. The console offers no `!` commands for Pi, and the extension refuses `user_bash`. These narrow "tools registered by other extensions" in the list of what is not confined to extensions the operator opts in. *Built 2026-10-29:* `-e builtin:mcp` would start the operator's `mcp.json` servers, so the launch is `-ne -e <extension>` alone, and the Conductor's extension composes Pi's MCP support with an empty server list before registering the console's server. Nothing a command writes may configure or repoint git, since the console runs git there unsandboxed; it may still commit, in a main checkout or a linked Worktree. The git directory is writable except what configures git, runs code or points it elsewhere (`config`, `config.worktree`, `hooks`, `info`, `modules`, `commondir`, `worktrees`, `remotes`, `branches`, a linked Worktree's `.git` file, `commondir` and `gitdir`). A deny on a missing path leaves an empty placeholder while a command runs, and an empty `commondir` stops git, so the extension gives a main checkout a `commondir` of `.` (what git takes when there is none), and its missing protected folders empty, before protecting them. Since a command can still leave a repository behind that git would trust (a broken `.git` with a bare repository at the Worktree root, a nested repository added as a submodule), the console's own git always runs with `safe.bareRepository=explicit`, `diff.ignoreSubmodules=dirty`, `fetch.recurseSubmodules=false`, `submodule.recurse=false`, `core.fsmonitor=false` and `core.hooksPath=/dev/null`, set in its environment so no configuration file can undo them. The file tools also refuse `/proc`, which in Pi's own process shows its environment. Pi's own needs (its state directory and credentials, the Worktree's `.pi`) are not rendered at boot: the extension adds them at each session start, since only it knows Pi's real state directory; the rendered policy carries the operator's lists and the console's own state and repositories.
